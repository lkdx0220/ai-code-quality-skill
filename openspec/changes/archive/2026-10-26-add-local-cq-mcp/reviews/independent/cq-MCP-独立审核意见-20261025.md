## 1. 总体判断

**修改后可实施。**

架构与取舍是成立的：本地 stdio、单项目绑定、子进程隔离、8 工具面、不开放写工具、pytest 启动期 opt-in、原始门结果与证据完整性并列、不做 MCP Tasks——这些决定我认可，不建议推翻（见 §7）。

但"证据完整性"这条核心卖点目前有 **三处契约空洞**，会在首版直接落空：

- 没有**完成标记**，服务无法判定一个非自己创建的 run 是否写完（M06）；
- 没有**输入指纹的真源**，MCP 要复刻核心的排除规则才能算 freshness（M02）；
- **assessment 的合成规则**让默认配置下恒为 `partial`，同时允许 `assessment=pass` 与 `freshness=stale` 并存（M01）。

另有四处契约在现有核心或方案里**找不到实现入口**：comparability 需要的配置字段不在 `summary.config` 里（M04）；`run_id` 碰撞的异常与退出码未定义，且退出码映射表漏了 scan 1、gate/diff 3（M03）；跨进程锁的原子原语、位置与陈旧恢复未定（M05）；单条超预算 finding 的分页推进语义未定（M07）。

这些不是"实现时自然会解决"的细节：它们决定返回字段是否可信，必须在写代码前定稿。**不建议**因此改成本仓 in-process 调用——子进程隔离带来的爆炸半径控制和"CLI 即契约"的可验证性，值这个复杂度；真正该做的是把契约补到核心侧（见 M02/M06），而不是让 MCP 去猜。

### M01（阻断）assessment 在默认策略下恒为 partial，且 stale 仍可能 pass

- **位置**：design §4「assessment 判定优先级」、§2「默认 pytest 禁用」；`gate.py:150-163`、`gate.py:182-187`。
- **触发**：使用默认启动策略（不含 pytest）。覆盖率检查永远 `skipped=True`（`coverage.json` 只由 pytest adapter 产生，没有它 `_coverage_percent` 返回 None）；不传 `base_run_id` 时 `new_blocker_high` 也 `skipped=True`。按 §4，`skipped` ⇒ `partial`。
- **影响**：默认配置下**每一次 gate 都是 partial**，`assessment` 失去区分力，消费者会学会忽略它——恰好是设计想避免的"读者误读单一字段"。反向更危险：§4 的优先级里 freshness 不参与，`assessment=pass` 与 `freshness=stale` 可以同时出现，与 §7「不得据其宣称当前代码合格」、§4「消费者以 assessment 判断质量」直接冲突。此外仓库无测试时，即使开启 pytest 也永远无法到达 pass（`pytest_cov.py:55-63`）。
- **最小修订**：把三条轴拆开，不要在一个字段里混：(1) `declared_scope`（启动策略 + 本次 adapter 集 + 是否传基线）；(2) `evidence`（实际执行与产物合法性）；(3) 由两者派生的单一 `verdict`，优先级 `fail > cannot_judge > pass_stale > pass_with_gaps > pass`，`freshness != current` 时 verdict 不得为 `pass`；策略性未启用记 `out_of_scope`（不计入 incomplete），执行期 skipped/error 才记 `gap`。`reasons` 用机器可读 code + 文本。
- **验证**：T10 增三条断言——默认策略 + 无基线 ⇒ `verdict=pass_with_gaps`（或 `cannot_judge`）且 reasons 含 `COVERAGE_OUT_OF_SCOPE`/`NO_BASELINE`；扫描后改源文件 ⇒ `verdict=pass_stale`；pytest opt-in + 覆盖率达阈值 + 有基线 ⇒ `verdict=pass`。

### M02（高）输入指纹缺核心真源

- **位置**：design §7「记录被扫描源/测试文件…清单和 SHA256」；`targets.py:15-46`（`EXCLUDE_DIR_NAMES`）、`targets.py:261-303`、`scan.py:205`。
- **触发**：任何一次需要计算 `unstable`/`freshness` 的扫描。
- **影响**：`summary.scanned_targets` 是**顶层入口路径**（目录或散文件），不是逐文件清单，也没有摘要。MCP 要么自己 walk 项目（必须复刻 `EXCLUDE_DIR_NAMES`、`.gitignore` 子集、`src` 布局规则），要么放弃"逐文件指纹"。复刻必然漂移：核心以后加一个排除目录，MCP 的"输入未变"就会说谎。这直接削弱 CQ-MCP-11。
- **最小修订**：核心在 `summary` 增加 `inputs`（`{rules_version, files:[{path, sha256, kind}], truncated:false}`），或提供 `cq inputs --json`；MCP 只读，不自行枚举。MODIFIED 表补 `scan.py`（已在表内）+ `targets.py`。配置文件摘要（`cq.toml`、`.cq.toml`、`.cq/suppressions.json`）单列为 `config_digests`，不要与源码文件混在一张表里。
- **验证**：T14 断言 `inputs.files` 集合等于工具实际展开的 `.py` 集合（可用 ruff/pytest 的入口参数对照），并覆盖"新增未跟踪 .py""改名""删除"三种。

### M03（高）run_id 碰撞与退出码契约不完整

- **位置**：spec CQ-MCP-06；design §6；`scan.py:53-55`、`cli.py:749`、`cli.py:752-756`。
- **触发**：自定义 `--run-id` 命中已存在目录；或默认命名同秒两次扫描。
- **影响**：三处缺口。(1) 核心改成 `exist_ok=False` 后抛 `FileExistsError`，`_run_scan_command` 只捕 `FileNotFoundError/ValueError` → traceback，Python 退出码 1，stderr 是堆栈而不是可映射的错误；(2) 退出码映射表根本没有 **scan exit 1**（现有核心用它表示项目不存在/adapter 非法），也没有 **gate/diff exit 3**（`RunNotFoundError`/`ValueError` 的既定语义）——按表会被归进"未知 exit"，丢掉 `RUN_NOT_FOUND` 的区分；(3) 默认命名从"同秒隐式复用"改为"明确失败"是**可见的 CLI 行为变更**，proposal 却写"不改变正常旧命令结果语义"。
- **最小修订**：新增 `RunExistsError`（或 `ValueError` 子类），CLI 捕获后映射为**独立的非零退出码**（建议 3，与其它子命令的"配置/引用错误"一致；若坚持 1，必须在 spec 写明 scan 1 的语义），并让 stdout/stderr 带机器可读的 `RUN_COLLISION`；映射表补齐 scan 1、gate/diff 3；proposal 明写默认命名的行为变更；MCP 的 `run_id`/`base_run_id` 校验必须与核心 `BASELINE_NAME_CHARS` 对齐（否则 MCP 接受的引用会被 CLI 判非法），或者核心放宽 `validate_baseline_name` 只禁分隔符（见 O08）。
- **验证**：T06 增"预置目录（含旧文件）→ 非零退出且旧文件 hash 不变"；T09 增 scan exit 1、gate exit 3 两条映射用例。

### M04（高）comparability 字段缺失，MODIFIED 表漏项

- **位置**：design §7/§8（披露 scope/adapter/tool version/config 并据此判 `comparable`）；`config.py:107-119`；proposal MODIFIED 表。
- **触发**：两次 run 的 `respect_gitignore`、`enabled_adapters` 或 `no_deepsec` 不同。
- **影响**：`Config.snapshot()` 只含 python/deepsec/timeout/覆盖率/vulture/cc/mi，**不含** `enabled_adapters`、`no_deepsec`、`respect_gitignore`。adapter 可从 `summary.tools[].name` 反推，但 `respect_gitignore` 直接改变扫描面，无法从现有字段判出。结果只能是：要么漏判（声称可比），要么 MCP 一律声明"不可判定"，让 `comparable` 恒 false、字段作废。MODIFIED 表也没有 `config.py`。
- **最小修订**：`snapshot()` 纯增三个字段（无破坏），MODIFIED 补 `config.py`；若不想动核心，就把"可比"定义收窄为 `(scope, tools[].name, tools[].version, cq_version, scanned_targets)`，并明确 `respect_gitignore`/suppression 摘要为 unknown ⇒ `comparable=false`。
- **验证**：T13 构造仅 `respect_gitignore` 不同的两个 run，断言 `comparable=false` 且 reasons 指名该字段。

### M05（高）跨进程锁：原语、位置、陈旧恢复

- **位置**：design §5（`<project>/audits/.cq-mcp-lock/`）、§7（状态清理由用户手工）、spec CQ-MCP-07（陈旧锁）。
- **触发**：服务被强杀/断电；用户清理 `audits/`；并发两个实例。
- **影响**：目录锁在进程死亡后必然残留，而 design 又禁止"未确认抢锁"——一次硬崩就要人工删目录才能再扫，且没有恢复入口。锁放在 `audits/` 内还与"audits 可整体导出/清理"的运维语义冲突（README:152 明确说目标仓库只多 `audits/`，用户会以为整目录可删）。方案也没写原子原语：`mkdir` 后写 `owner.json` 之间存在半写窗口。
- **最小修订**：改用 **OS 咨询锁**（Windows `msvcrt.locking`、POSIX `fcntl.flock`）持有 `<project>/.cq-mcp.lock`（项目根，不在 audits 内）；进程退出/崩溃由内核自动释放，删掉"陈旧锁需人工清理"整条分支，文件内容只存 `{pid, start_time, job_id}` 供诊断。若坚持锁目录，必须定义"owner 记录缺失 ⇒ 视为陈旧"的判定并允许自动回收。
- **验证**：T08 改为"强杀服务后立即重启，无需人工干预即可再次扫描"；T05 保持两进程并发。

### M06（高）缺完成标记，无法判定 run 是否写完

- **位置**：design §7「拒绝活动 run 和未完成产物」；`scan.py:158-174`（先 summary，再 findings，最后 report）、`runs.py:46-63`（只看 `summary.json` 是否存在）。
- **触发**：另一个 state-dir 的实例、旧 CLI 直接扫描、被 kill 的扫描、同秒复用的历史目录。
- **影响**：MCP 只能对自己台账里的 job 判"活动"，对其它来源无法判"写完"。当前写入顺序使"summary 已写、findings 未写"成为可见状态：`resolve_run_dir` 会认它，`load_run` 会抛读取失败；在历史同秒复用目录里甚至会出现"新 summary + 旧 findings"的混合。读者无法区分"正在写"与"损坏"。
- **最小修订**：核心在全部产物写完并 fsync 后写 `audits/<run>/.complete`（含 `run_id`、`summary.sha256`、`findings.sha256`、`cq_version`）；所有读者以该标记判完成，缺标记的旧 run 允许导入但 `complete=unknown`、`freshness=unknown`。MODIFIED 表补 `scan.py`。
- **验证**：T11 用拖慢的 fixture 在扫描中读取 ⇒ 未就绪（不是空页）；T14 旧 run 无标记 ⇒ `unknown`。

### M07（中）超长单条 finding 的分页推进与游标方案

- **位置**：design §7（每页 ≤100 项 / 128 KiB；单项超限走 artifact）；spec CQ-MCP-09。
- **触发**：一条 finding 的 `message`+`evidence` 超过页预算（中文长 traceback 很容易）。
- **影响**：该项放不进页 ⇒ 返回空页 + 同一个 `next_cursor` ⇒ 客户端死循环；若跳过该项 ⇒ 违反"完整遍历无重无漏"。另外游标方案写着"不可伪造**或**服务登记"，两者成本与生命周期完全不同，没定就没法实现。
- **最小修订**：定义占位语义——`items[i] = {id, inline:false, artifact_id, size_chars}` 且 cursor 前进；或整页返回 `OUTPUT_TOO_LARGE` + `artifact_id`（此时不返回 `next_cursor`，客户端改走 artifact_get）。游标二选一定稿：HMAC（密钥持久化在 state-dir，重启可验）**或**服务登记表（设上限、随 run 清理）。
- **验证**：T12 增"单条 200 KB evidence"和"恰好卡在页边界"两个用例，断言 10 页内取完、无重复、无非空页死循环。

### M08（中）gate/diff 写 run 目录的两个后果

- **位置**：design §6；`cli.py:588-589`（先写 diff.json 再打印）、`cli.py:631-636`（写 gate.json）。
- **触发**：audits 只读（CI 产物、只读挂载、权限受限）；同一 run 多次 gate；导入的历史 run。
- **影响**：写盘失败是未捕获 `OSError` ⇒ traceback、stdout 无 JSON ⇒ 整个 gate/diff 不可用，尽管它本质只读；同时会覆盖该 run 历史 `gate.json`（design 已披露，但对"只读调用"仍意外）。
- **最小修订**：CLI 增 `--no-save`（MCP 固定使用），或写盘改为 best-effort（失败只写 stderr 警告，不影响 stdout 与退出码）；权威副本由 MCP 快照承担。
- **验证**：T16 增"只读 run 目录/只读 audits"用例：gate/diff 仍返回完整结果，退出码不被写盘失败污染。

### M09（中）去重与抢锁的竞态

- **位置**：design §3「先完成该台账的去重查询，再尝试锁和创建 job」；spec CQ-MCP-05。
- **触发**：两个客户端（或两个实例）同时用同一 `request_key` 提交。
- **影响**：两者都查不到既有 job，一个拿到锁，另一个拿到 `PROJECT_BUSY`；而 `request_key` 的设计目标恰恰是让重试拿到原 job。这是可稳定复现的语义违背，不是理论竞态。
- **最小修订**：拿到锁后**在锁内二次查重**再创建；或先原子写 dedup 预留条目再抢锁（抢锁失败删除预留）。参数规范化要含 adapter 的集合语义（排序去重后再算摘要）。
- **验证**：T05 增双线程同 key 并发，断言返回同一 `job_id`，或明确 `REQUEST_CONFLICT`（参数不同），不得出现 `PROJECT_BUSY`。

### M10（中）默认总期限与核心超时预算不匹配，超时是无产物

- **位置**：design §2（默认 900s）；`config.py:17-22`（default 300 / mypy 600 / deepsec 600）；`scan.py:66-76`。
- **触发**：大仓库、冷缓存、deepsec 全量。
- **影响**：7 个默认 adapter 的 per-adapter 超时之和是 `5×300 + 2×600 = 2700s`，MCP 的 900s 会在核心仍认为"在预算内"时杀掉扫描。更关键的是 `run_scan` 在所有 adapter 跑完后才写产物，被杀后目录里只有 `raw/`——**没有 summary、没有 findings**，所以 design 所说的"partial 产物"实际不存在（能留下的只有原始日志）。
- **最小修订**：默认总期限 = `max(900, sum(per-adapter timeouts) + 60)`，或干脆不设总期限（只保留 per-call `timeout_seconds` 与取消）；文档明确"超时 = 无结论、无产物"；若要 partial 证据，另立"核心按 adapter 增量落盘"的变更，不塞进首版。
- **验证**：T07 用一个必然超过单工具超时的 fixture，断言 `job=timed_out`、无 summary、`findings_get` 明确"未就绪"而不是空 findings。

### M11（中）`--adapters ""` 在核心侧回退为全部 adapter

- **位置**：`adapters/__init__.py:29-31`（`if not enabled: return list(ALL_ADAPTERS)`）、`cli.py:749`（空串解析成 `[]`）、`scan.py:59`（`enabled_adapters or cfg.enabled_adapters`）。
- **触发**：MCP 拼参 bug、未来重构、或任何人手工 `cq scan --adapters ""`。
- **影响**：核心"显式空列表"= 全部 adapter（含 pytest），于是"pytest 默认禁用"完全依赖 MCP 层自律。pytest 会执行目标项目代码，这是首版最需要守住的边界，不该只有一层。
- **最小修订**：核心把显式空列表视为错误（`get_adapters([])` 与 `--adapters ""` 都拒绝，exit 3），让"非空"成为核心不变量；MCP 仍传显式非空列表。改动约 3 行，纳入 MODIFIED。
- **验证**：T04 增 `cq scan --adapters ""` 断言非零退出且 pytest 未执行（fixture 留执行痕迹）。

### M12（中）"必须脱敏"是不可达的绝对断言

- **位置**：spec CQ-MCP-12；`redact.py:15-44`。
- **触发**：分析器输出里出现未覆盖形态的凭据（如 `Authorization: Bearer <opaque>`、任意高熵字符串）。
- **影响**：`redact` 只覆盖 9 条规则（AKIA/gh*/xox*/sk-*/AIza/JWT/私钥/赋值形态/连接串）。"响应、stderr、任务日志和错误必须脱敏"写成绝对义务，验收无法达成——一个红队用例即可证伪；同时会让作者误以为"脱敏已解决"。
- **最小修订**：改为"已知形态凭据 + 赋值形态（列清单）已脱敏；不读取 `.env`；不回传 `raw/`；不保证任意未知形态"；补 `Authorization`/`Bearer` 规则；spec 写明残余风险与扩规则流程。
- **验证**：T15 分两组——已知形态断言被替换；未知形态只断言"不因此判失败/不泄露到日志原值以外的保证不存在"（即不写不可达断言）。

### M13（中）findings_get 没有新鲜度信号

- **位置**：design §3（findings 返回 items/total/returned/next_cursor/digest）、§7（freshness 只在 gate 段落定义）；spec CQ-MCP-11。
- **触发**：扫描完成后源文件/配置发生变化，客户端仍调用 findings_get 取结论。
- **影响**：Agent 最常用的路径是"读 findings 就下结论"，而该路径拿不到 `freshness`/`completeness`；与 spec 11"读取时检测变化须标记 stale"不一致（"读取"当然包括 findings_get）。
- **最小修订**：所有读 run 的工具共享一个 `run_header`（`run_id`/`scope`/`created_at`/`complete`/`freshness`/`completeness`/`config_digest`），findings_get 必须带。
- **验证**：T14 增 findings_get 的 stale 断言。

这些不要求现在改规格，但必须先用原型或实测排除，再定稿措辞。

| ID | 风险 | 为什么要先验 | 建议做法 |
|---|---|---|---|
| R01 | Windows Job Object 的**无竞态**接入 | `subprocess.Popen` 不暴露 `CREATE_SUSPENDED`；先 `Popen` 再 `AssignProcessToJobObject` 存在"子进程已派生子进程"的窗口 | 用 ctypes 走 `CreateProcessW(CREATE_SUSPENDED)` → Assign → Resume；或可选依赖引入 psutil（`children(recursive=True)` + job 兜底）。先写 30 行原型验证 cancel / timeout / 父进程被 kill 三场景 |

## 6. 质量门失败要不要映射成 MCP 调用错误

**不要。** 理由四条：

1. `isError` 的协议语义是"工具没有完成它的工作"。质量门返回"不通过"恰恰是工具完成了工作；映射成错误会让客户端重试、跳过或展示成故障，把最有价值的报告藏起来。
2. 不少 Agent 以 `isError` 作为"换工具/放弃"的分支条件；质量失败触发回退会直接摧毁工作流（例如改用别的扫描器）。
3. 设计把 gate exit 1 归为有效失败、exit 2 归为无法判断，方向是对的；缺口只在 exit 3（run 不存在）——它属于引用错误，应进 `isError`，不要混进 `cannot_judge`。
4. 领域结果需要保留完整 payload（`checks`/`ratings`/`next_steps`），`isError=true` 的结果在不少客户端里不会被当作正常数据渲染。

因此：`gate exit 0/1/2`、`diff exit 0/1`、`scan exit 0/2`、`doctor exit 0/2` 全部 `isError=false`，用 `verdict`/`cannot_judge` 表达结论；`gate exit 3`、`PROJECT_BUSY`、`STATE_LIMIT`、参数/越界/完整性/IO 错误才 `isError=true`，并带可操作 code。

## 7. 范围与排期建议

**不建议砍工具面。** 8 个工具里没有一个是"可留可不留"的：cancel 是长任务的前提，artifact_get 是"不截断 JSON"的前提，doctor 是信任边界的入口。真正该砍的是**验收面的广度**，不是能力面。

如果必须压缩首版，我建议的切割顺序是：

1. Linux 的崩溃回收降级为"取消尽力 + 文档声明不回收"（R02），Windows 先做到无竞态。
2. 第二个真实客户端从"发布阻塞"降为"1.0 门槛"（R08），首版用 1 个真实宿主 + 官方协议客户端。
3. `comparability` 的配置判定降级为"只比 scope/adapter/tool version/scanned_targets"，其余标 unknown（M04 的替代方案），把 `respect_gitignore` 的补字段留到 v1.1。
4. 若仍要再砍，才考虑把 `assessment` 降级为"三值 + 独立 evidence"，把解释权交回 Skill/Agent（这能一次性消掉 M01 的大部分复杂度）。

**不要砍**：完成标记（M06）、输入指纹真源（M02）、锁的崩溃自愈（M05）、pytest 的核心侧防护（M11）。这四项是"服务说实话"的底座，砍掉之后 MCP 只是给 CLI 套了一层会撒谎的壳。

## 8. 结论

- **总体判断**：修改后可实施。
- **开工前必须定稿**：M01–M06（含 M03 的退出码映射表）。
- **发布前必须定稿**：M07–M13，R01–R10 中与本机环境相关的项。
- **本意见的证据边界**：静态规格审核 + 只读源码核对；13 个源文件 SHA256 已复算一致，主仓 HEAD 已核对；未安装、未运行测试、未改代码、未发布，未阅读既有模型意见。运行时结论（SDK、客户端、进程树、编码）均为"待确认"或"须实测"，不构成已验收。
