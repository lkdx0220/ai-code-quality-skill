### P2-1 非UTF-8字节损坏的marker/产物越过结构化错误契约；triage/fix/suppress裸崩溃

- 代码：
  - `src/ai_code_quality/evidence.py:120`（`marker.read_text(encoding="utf-8")`）与 `:143-155`（except元组 `(FileNotFoundError, IsADirectoryError, json.JSONDecodeError, KeyError, TypeError, AttributeError)` + `OSError`，**不含UnicodeDecodeError**）
  - `src/ai_code_quality/runs.py:73,83`（summary/findings `read_text`）与 `:84`（`except (OSError, json.JSONDecodeError)`，同样不含）
  - `src/ai_code_quality/cli.py:526-533`（`_load_run_or_error` 仅 `except LookupError`）
- 触发条件：schema2 run 的 `.complete.json`、`summary.json` 或 `findings.json` 中出现非法UTF-8字节（二进制级损坏/半写的字节态，区别于已正确处理的ASCII垃圾损坏）。
- 预期：core-implementation.md已实施第4条声明"损坏…拒绝，不把损坏JSON当空finding"，即结构化 `INVALID_ARTIFACT` 拒绝。
- 实际（已实测，`testwork/exp1_corrupt_marker.py`，复现命令：对fixture run写入 `b'\xff\xfe{"schema_version":2}'` 到 `.complete.json` 后调 `python -m ai_code_quality.cli gate|triage --project <proj> --run run-001 --format json`）：
  - gate/diff：exit3、无崩溃，但错误码为 `INVALID_ARGUMENT`（`{"error":{"code":"INVALID_ARGUMENT","message":"'utf-8' codec can't decode byte 0xff..."}}`）——把"产物损坏"误标为"调用参数错误"；
  - triage/fix/suppress：**裸Traceback、exit1**（UnicodeDecodeError未捕获）。triage的exit1是合法业务返回码语义，脚本可能误读；traceback未走 `_command_error` 脱敏通道。
- 影响评估：ASCII垃圾损坏路径已被33项负控覆盖；本缺口触发面窄（二进制级损坏）。MCP直接消费的scan/gate/diff/inputs四条路径均无崩溃，但gate/diff的错误码误标会传导到MCP错误映射层（design §4将INVALID_ARGUMENT类定义为调用方过错）。`summary/findings` 的同类缺口在基线即存在（旧有），`.complete.json` 是本批新增文件面。
- 最小修正：`evidence.py` 与 `runs.py` 的except元组补 `UnicodeDecodeError`（或统一 `ValueError`）；`cli._load_run_or_error` 扩为 `except (LookupError, ValueError)`。补一个非UTF-8损坏负控测试。
- MCP施工前必须修复：**是**（本批自定契约的实现缺口，修复成本一行级；不修则MCP层须自行兜底 Broad-except）。
