1. **拒绝了我对 inputs 的过强断言**。我 r01 要求「inputs 集合 == 工具实际展开的 .py 集合」，但 ruff/pytest 的排除、动态 import、运行时数据都可能超出目录 argv 能证明的范围。r02 改为「cq 监视集合，不是分析器实际读取全集」，并把验证改为共享规则夹具——这是对的，我原来的验收条件不可满足。

## 3. 新发现问题

### N01（高，默认策略）默认 adapter 集与默认 verdict 自相矛盾

- **位置**：design §3「省略 adapters = 冻结默认七个非 pytest adapter」、§4 第 3/5 步与「默认无 pytest/无 baseline 且其他选定工具正常时应得 pass_with_gaps；缺 DeepSec 或 import-linter 配置导致选定工具 skipped 则 cannot_judge」。
- **触发**：最常见的机器/仓库——未安装 deepsec（doctor 里 `optional=True`），或项目没有 `.importlinter`/`pyproject [tool.importlinter]`/`setup.cfg` 配置。`import_linter.py:63-73`、`deepsec_adapter.py:136-140` 对这些情况都返回 `status=skipped`。
- **影响**：默认七项包含这两个**可选**分析器；它们 skipped 即被视为 runtime gap → 第 3 步 → `verdict=cannot_judge`。也就是说，**默认配置在大多数机器上永远得不到 pass_with_gaps**，只有装了 deepsec 且配了 import-linter 的仓库才行。这与 r02 自己写的默认期望（pass_with_gaps）直接冲突，也是 r01「assessment 恒 partial」问题的变体：字段不再恒 partial，但默认恒 cannot_judge。另外，core 的 `doctor` 把这两项标为 optional（缺失可降级），`gate.py` 也不因 skipped 失败——MCP 的默认策略比核心更严，却没有区分「可选工具缺失」与「已选工具执行失败」。
- **最小修订**（二选一，改动都不大）：
  (a) 默认集改为核心 required 五项（ruff-check、ruff-format、mypy、radon、vulture），import-linter/deepsec 改为显式选择——选中后 skipped 才是真 gap（改默认列表 + 一致性测试）；
  (b) 保留七项，但把 `missing_tool`/`no_config` 且核心标 optional 的 skip 归入 `declared_scope.out_of_scope`，在 `pass_with_gaps` 的 reasons 里点名，而不是 runtime gap（在 gap 分类处加一条 optional 判定）。
  无论哪种，都应把「默认集包含哪些、为什么」写进工具描述首页。
- **验证**：T10 增两条——无 deepsec、无 import-linter 配置的默认扫描 ⇒ `pass_with_gaps` 且 reasons 点名两项未含；显式选择 deepsec 但未安装 ⇒ `cannot_judge`。

### N02（中）`verify_current=false` 是死参数，60s 新鲜度检查在大型仓库是硬墙

- **位置**：design §3 `cq_gate ... verify_current?(true)`、§2「显式新鲜度检查另限 60s」、§6.277「findings_get 默认不重 hash，freshness=unknown；gate 默认 true；超时保留历史报告但 verdict cannot_judge」、§4 第 3 步「freshness=unknown/unstable → cannot_judge」。
- **触发**：调用方传 `verify_current=false`；或仓库大到 60s 内算不完 inputs 摘要（十万级文件、网络盘、冷缓存）。
- **影响**：按 §6.277 的同口径，`false` ⇒ freshness=unknown ⇒ 按第 3 步只能 cannot_judge，所以这个参数唯一的作用是「强制不给结论」；`true` ⇒ 60s 上限一旦超时就 cannot_judge。两条路径叠加后，大型仓库的 gate **永远无法给出任何正向 verdict**，而且没有配置项能放宽。这会让 gate 在最需要它的仓库上不可用。（若作者本意是 `false` 时沿用扫描时记录的 freshness，则必须写明该值不代表当前工作区并被 verdict 区分，否则等于把历史 current 当成现在 current——这正是 r01 M01 要防的误读。）
- **最小修订**：把「扫描时的 freshness」与「本次是否复算」拆成两个字段：`scan_freshness`（扫描完成时记录，含 checked_at）与 `verified_now`（本次调用是否复算）。然后：
  - `verify_current=false` ⇒ `verdict=pass_historical`（新增一个明确标注「仅历史版本通过、未验证当前工作区」的值），或直接去掉该参数只保留 true；
  - 新鲜度检查期限改为启动配置可调（如 60–600s），超时给 `FRESHNESS_TIMEOUT` 而不是笼统的 unknown。
  这样既守住「stale/unknown 不得无条件 pass」，也不会让大仓库无路可走。
- **验证**：T10 增「verify_current=false ⇒ verdict=pass_historical（或明确拒绝该参数）」；T14 增「新鲜度检查超时 ⇒ 明确 code，而非无差别 unknown」；用一个 >60s 的夹具仓库验证期限可调。

### N03（中）根锁文件污染目标仓库，并使只读项目根不可用

- **位置**：design §5「项目执行锁移到 `<project>/.cq-mcp.lock`，稳定文件不删不重建」、§5「只读整个项目根不在首版支持范围」、proposal「可见行为变化」。
- **触发**：任何一次 MCP 扫描/doctor/gate/diff（都会持锁）；用户在只读 checkout（CI 产物、挂载卷）上运行；用户执行 `git status`。
- **影响**：三个具体后果。
  1. 目标仓库根多出一个未跟踪文件 `.cq-mcp.lock`。core 的 `get_git_info()` 用 `git status --porcelain` 统计 dirty，未跟踪文件会算进去——**MCP 扫描出的 `summary.git.dirty_files` 会比同一仓库的 CLI 扫描多 1**，T20 的 CLI 对照可能看到这个差异；用户 `git add -A` 还可能误提交。
  2. core 的既有承诺是「目标仓库 git status 不变（只多 `audits/`）」（README:152），MCP 打破了它；proposal 的「可见行为变化」只列了碰撞、空 adapter、schema2、--no-save、exit4，没列这个新文件。
  3. 只读项目根无法创建锁文件 ⇒ gate/diff 不可用，尽管设计说「只读 audits 可用」。现实中「audits 只读但根可写」很少见，这个组合测试（T16）覆盖不到真实只读场景。
- **最小修订**：把锁移到用户级运行时目录，按规范化项目路径的哈希命名（Windows `%LOCALAPPDATA%\cq-mcp\locks\<sha256>.lock`；POSIX `${XDG_RUNTIME_DIR:-~/.cache}/cq-mcp/locks/…`），跨 state-dir 仍共享同一文件，且不写仓库、不依赖根可写；文档写明「跨用户并发不保证串行」。若坚持放项目根，必须把该文件写进「可见行为变化」、说明 `git.dirty_files` 差异、并接受只读根不支持。
- **验证**：T03/T16 增「只读项目根 + 可写 state ⇒ gate/diff 可用」与「MCP 扫描后 `git status --porcelain` 与 CLI 扫描一致（除 audits）」。

### N04（中）容量模型不自洽：256 MiB / 1000 任务 / 10000 游标 与「每次预留最坏 capture+快照」无法同时成立

- **位置**：design §8「state 默认 256MiB、1000 任务、10000 游标……操作预留最坏 capture+快照空间后才接受」；§7「gate/diff 每次以 operation_id 存不可变快照」；§8「不删既有任务/去重键/快照」。
- **触发**：连续执行较大规模的 gate/diff（每次快照上限对应 8MiB stdout）。
- **影响**：如果「预留」是持久的，单次 gate 预留 8MiB ⇒ 256MiB 只够约 32 次操作，1000 任务/10000 游标的上限根本达不到；如果是瞬态的（操作结束释放、按实际大小计费），那「预留最坏空间后才接受」对并发峰值仍成立，但设计没说。再叠加「每次 gate/diff 都存快照、且不删既有快照」，256MiB 的寿命是可预测的（约等于实际快照总量），却没有给出「何时满、满了以后用户怎么做」的量化预期。这不是正确性问题，但会让 STATE_LIMIT 比用户预期早很多到来。
- **最小修订**：明确三件事——(a) 预留是**事务内瞬态**还是持久占用（建议瞬态：接受前检查 `当前已用 + 本次最坏`，提交后按实际大小计费）；(b) 快照只在结果超出 inline 预算时才落盘（小结果不存整份），单快照设上限；(c) 给出「典型操作 × 次数 → 预计用量」与状态清理指引，并在 `job_get` 的 capacity 里分项显示（SQLite、快照、日志、游标）。
- **验证**：T22 增「1000 个小任务 + 100 个大 gate 快照」的组合用例，断言要么在预算内全部接受，要么在明确阈值处返回 STATE_LIMIT 且既有读取可用；并断言预留不会因并发两个请求而超卖。
